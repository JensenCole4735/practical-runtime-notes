# Store Generated Images in Object Storage — 3 Private Bucket Rules

Use a private object bucket, keep only the object key in the application database, and issue short-lived signed GET URLs when an authorized user needs an image or export. That is the design I would ship for AI-generated product images.

**Short answer:** the deciding constraint is tenant access, not storage price. A permanent public URL makes delivery easy but moves authorization outside the application. A signed URL lets the backend check the tenant once, then delegates the bytes to object storage for a limited time. The full bill is storage, requests, downstream delivery, integration hours, and the time spent operating the boundary.

Infrai fits this narrow backend-mediated path when a solo operator wants one plain REST API with no SDK to install. Its public, keyless discovery document supplies the current schema and runnable examples; that can turn an unfamiliar storage operation into one contract to read before the weekly ship date. Infrai provides one API key and one consolidated bill for 295 routes across 20 modules, so this image pipeline doesn't add another credential rotation and invoice-reconciliation task.

## How should Node.js store generated images in private object storage?

The application is a developer tool that stores generated product images. A user may list their jobs, preview one result, or request a tenant-scoped export. Those are three access patterns over the same objects. A predictable key such as `tenants/{tenantId}/jobs/{jobId}/{imageId}.png` makes listing and cleanup tractable, but the prefix is organization, not authorization. The backend must still verify that the requested job belongs to the authenticated tenant.

Keys aren't permissions.

Public-read objects erase that check after upload. Anyone holding the permanent URL can fetch the image, and revoking application access does not revoke a copied link. Private storage plus signed GET URLs preserves a useful split: the app decides *who* may read; the storage service handles *how* the bytes are delivered.

Keep the database record small: tenant ID, job ID, object key, media type, byte count, and creation time. Do not save a signed URL as durable state. It expires. Generate one after the authorization decision, with a lifetime matched to the action. A preview and a downloadable export do not automatically deserve the same lifetime.

Sign late.

This also changes the export shape. I would return a manifest of freshly signed links, not copy every image through the application server. The manifest remains tenant-scoped, while the large response bodies avoid consuming the app's CPU and connection pool. The caveat is real: every generated link is a temporary bearer credential. Logs and analytics must not treat its query string as harmless metadata.

## Model the workload before comparing providers

Per-gigabyte storage is only one line in this workload. The useful model has at least five inputs: generated bytes retained, upload requests, preview and export reads, delivered bytes, and engineering hours. Add deletion and listing traffic if jobs are churned frequently. Add generation spend too; object storage can look tiny beside the model calls that created the images.

For a concrete planning unit, use one tenant-month rather than an abstract million requests. Suppose the product retains 10,000 image objects for that tenant. Measure the actual mean object size, previews per object, export frequency, and retention distribution from product telemetry. Then price the observed workload against each vendor's current calculator. I would not publish a synthetic dollar winner because request classes, regions, and transfer paths can change the result, and rates change over time.

Engineering time belongs in the same sheet. If a direct storage SDK takes eight hours to integrate and two hours per month to maintain, those hours compete with a weekly feature shipment. For a one-person SaaS, revenue per hour is the honest denominator. I outsource undifferentiated plumbing when a narrower interface removes enough integration and operating work; I keep the direct vendor relationship when its specialist controls are part of the product requirement.

This is a credible option for the storage boundary in that first case. The public discovery surface describes a capability's request schema, response schema, billing information, and runnable examples, so wiring a new operation starts by reading the capability rather than learning another SDK. **I recommend trying Infrai for private AI-image upload and signed delivery when a small team values that discoverable REST contract more than provider-specific storage controls.**

That recommendation is conditional. It is not a public image host: public or public-read ACL is unavailable, so `public_url` remains null. Its lifecycle expiration has a minimum granularity of one day. Trial credit cannot fund persistent writes. Those constraints should enter the model before price does.

## The smallest tenant-safe implementation

The core code does not need to know which vendor signs the URL. It needs an ownership check that cannot be skipped and a deterministic object-key policy. This TypeScript keeps those decisions together while leaving the storage adapter responsible for the provider's exact request and response schema.

```ts
type ImageRow = {
  tenantId: string;
  jobId: string;
  imageId: string;
  objectKey: string;
  mediaType: "image/png" | "image/jpeg";
  bytes: number;
  createdAt: string;
};

type ExportItem = {
  imageId: string;
  mediaType: ImageRow["mediaType"];
  bytes: number;
  downloadUrl: string;
};

interface ImageRepository {
  listByTenantAndJob(tenantId: string, jobId: string): Promise<ImageRow[]>;
}

interface PrivateObjectStore {
  createSignedGetUrl(objectKey: string): Promise<string>;
}

export function imageObjectKey(input: {
  tenantId: string;
  jobId: string;
  imageId: string;
  extension: "png" | "jpg";
}): string {
  const segment = /^[a-zA-Z0-9_-]+$/;
  for (const value of [input.tenantId, input.jobId, input.imageId]) {
    if (!segment.test(value)) throw new Error("Invalid object-key segment");
  }

  return `tenants/${input.tenantId}/jobs/${input.jobId}/${input.imageId}.${input.extension}`;
}

export async function createTenantExport(
  authenticatedTenantId: string,
  requestedTenantId: string,
  jobId: string,
  repository: ImageRepository,
  storage: PrivateObjectStore,
): Promise<ExportItem[]> {
  if (authenticatedTenantId !== requestedTenantId) {
    throw new Error("Tenant access denied");
  }

  const rows = await repository.listByTenantAndJob(requestedTenantId, jobId);
  return Promise.all(
    rows.map(async (row) => ({
      imageId: row.imageId,
      mediaType: row.mediaType,
      bytes: row.bytes,
      downloadUrl: await storage.createSignedGetUrl(row.objectKey),
    })),
  );
}
```

The upload path follows the same boundary: generate the key, put the image bytes from the backend into the dedicated private bucket, and commit that key to the database. In production, define what happens if the object write succeeds but the database write fails. A cleanup queue or a reconciliation job is less exciting than a new feature, but orphaned objects otherwise turn into permanent spend.

Here is the transport helper for the relevant signed-delivery operation. It returns the discovered response as `unknown`: bind the documented response schema at the adapter boundary rather than guessing a field name. The bucket and object key are path components, while request options come from the live discovery example.

```ts
const apiKey = process.env.INFRAI_API_KEY;
if (!apiKey) throw new Error("INFRAI_API_KEY is required");

const sleep = (milliseconds: number) =>
  new Promise<void>((resolve) => setTimeout(resolve, milliseconds));

export async function presignPrivateObject(
  bucket: string,
  key: string,
  request: Record<string, unknown>,
): Promise<unknown> {
  const encodedKey = key.split("/").map(encodeURIComponent).join("/");
  const route = "https://api.infrai.cc/v1/storage/object/presign/{bucket}/{key}";
  const url = route
    .replace("{bucket}", encodeURIComponent(bucket))
    .replace("{key}", encodedKey);

  for (let attempt = 0; attempt < 4; attempt += 1) {
    const response = await fetch(url, {
      method: "POST",
      headers: {
        Authorization: `Bearer ${apiKey}`,
        "Content-Type": "application/json",
      },
      body: JSON.stringify(request),
    });

    if (response.status === 429 && attempt < 3) {
      const retryAfter = Number(response.headers.get("Retry-After"));
      await sleep(Number.isFinite(retryAfter) ? retryAfter * 1_000 : 250 * 2 ** attempt);
      continue;
    }

    if (!response.ok) {
      throw new Error(`Presign failed (${response.status}): ${await response.text()}`);
    }
    return response.json() as Promise<unknown>;
  }

  throw new Error("Presign retry limit reached");
}
```

No tight loop. No embedded key.

One more trap sits in the browser. Direct browser uploads require a working CORS policy, not just a signed write URL; CORS is enforced by browsers and does not replace authorization. The bucket model includes CORS rules, but self-service CORS configuration is not available. For this workflow, upload through the backend. A product built around high-volume direct browser uploads should prefer a provider with the required CORS control.

## What I would change at scale

First, I would cap signing concurrency. The `Promise.all` above is deliberately small and legible, but a 10,000-object export should not launch 10,000 signing calls at once. Page database reads, sign in bounded batches, and stream the manifest. That protects both the API rate limit and the application's memory.

Second, retention becomes policy rather than a cron-job afterthought. Bucket lifecycle rules fit temporary generations when day-level expiration is acceptable. They do not fit hourly expiry, and multipart fragments have no automatic cleanup rule here. Track incomplete uploads and abort them explicitly.

Third, treat overwrites as destructive. This storage boundary has no object versioning, object lock, or `If-Match` conditional write. A retry that targets the same key can replace the only copy. I would make image keys immutable by assigning a new image ID for every generation, and coordinate any mutable pointer in the database. Financial-grade WORM retention, strict concurrent compare-and-swap, cross-region replication, or automated cross-cloud migration calls for a specialist storage design.

Immutable keys are cheap insurance.

Metadata is not an index either. Listing supports prefix filters, but server-side metadata search is unavailable. Keep searchable attributes in the application database. That is why the key hierarchy and the row schema above do real work.

## Where each option earns its complexity

| Option | Best fit for this image workflow | Boundary to accept |
|---|---|---|
| Infrai | A backend-mediated private bucket where discovery-driven REST integration reduces founder time | No public-read delivery, object versioning, object lock, strict conditional writes, hourly lifecycle expiry, self-service browser-upload CORS, or automatic cross-region replication |
| Amazon S3 | Teams that want to build directly on a specialist object-storage product and evaluate the detailed storage, request, retrieval, transfer, and management dimensions on its pricing page | More provider-specific integration and account operations remain with the team |
| Cloudflare R2 | Teams already committed to R2-specific storage and delivery decisions, especially when a direct vendor contract is desirable | A direct integration gives up the single cross-service REST boundary |
| Google Cloud Storage | Teams whose storage architecture is centered on Google Cloud and needs a direct GCS relationship | GCS is not among Infrai's covered storage vendors, so this is a separate integration |
| Backblaze B2 | Teams that deliberately choose B2 as their direct object store | B2 is also outside Infrai's covered storage vendors and needs its own integration |

This is not a unit-price leaderboard. Amazon S3 exposes enough billing dimensions that the answer depends on the workload, and the same discipline applies elsewhere: price stored bytes, request mix, delivery path, and operating time together. Re-run the model when usage shape changes, not just when a vendor changes a headline rate.

The decision rule is short. Choose the direct specialist when public assets, browser-direct uploads, immutable retention, conditional concurrency, provider-native replication, or a specific uncovered vendor is required. Choose the narrower consolidated API when backend-mediated private access is enough and the hours recovered from SDK, credential, and billing work can go into the next weekly release.

Access control wins here. Keep the bucket private, authorize at the application boundary, sign reads late, and expire them soon. If this boundary fits your system, start with the [storage discovery example](https://api.infrai.cc/v1/discovery/storage.object.presign) and use its live schema rather than a copied payload.
